# API-Load 透明网关设计

本文是 2026-10-20 的草案，下面的选项等逐项决策。

## 定位

API-Load 聚合各家上游的 key。下游发来什么路径、什么格式，就原样发给上游，只把访问密钥换成上游 key。产品的核心能力放在 key 的调度上，包括选哪个分组、选哪把 key、失败后怎么换、什么时候冷却、哪些请求要粘在同一把 key 上。

格式互转（Chat Completions、Responses、Anthropic Messages、Gemini 之间）保留为兜底能力，默认关闭，日志里标明。模型重定向继续放在 New API 做，API-Load 默认不改 model。

## 现状

数据面目前是强类型的白名单，结构是三层。

1. 入口路由表 `internal/gateway/router.go` 列出约 40 条固定路径，没列出的路径一律 404。
2. 每种渠道（37 个预设）声明自己支持哪些「协议 × 操作」，以及走原生还是转换。
3. 执行层按声明处理。原生路径基本透传，只改 4 处（换 key、按映射改 model、对齐 stream 并补 `include_usage`、删掉请求体里的 `api_key` 一类字段）；转换路径由 Bifrost 解析再重组，上游特有字段可能丢失。

这套结构带来下面这些问题。

| 问题 | 例子 |
|---|---|
| 新接口必须写代码才能用 | TTS、ASR、OCR 只有 Mistral 渠道能用；视频接口没有入口 |
| 预设漏声明就整条不通 | 硅基流动的 embeddings、rerank 以前一直 503 |
| 上游原生支持也被翻译 | OpenAI 兼容渠道的 Responses 一律翻译成 Chat Completions |
| base_url 规则因渠道而异 | `/v1` 要不要带取决于渠道类型（2026-10-20 已在解析层统一） |

## 目标结构

请求依次经过四层。

### 1. 入口识别接口，不设白名单

`/v1/**`、`/v1beta/**` 以及管理员配置的额外前缀全部进入数据面。一张「接口表」按路径模式识别请求属于哪一类，表里每一行描述下面四件事。

- 从哪里取 model（JSON 的 `model`、multipart 表单的 `model`、Gemini 路径里的模型段、或者没有 model）
- 上游线路格式（OpenAI、Anthropic、Gemini）
- 是否产生需要粘住的资源（文件、批任务、视频任务、Responses 存储）
- 怎么从响应里读用量

已知接口有完整的行；表里没有的路径按「OpenAI 线路格式 + JSON 里取 model」处理，后台可以添加或覆盖行。新接口出现时，多数情况一行配置就能接上，不用改代码。

### 2. 按 model 和线路格式选分组

分组描述的内容收敛为上游地址、一组 key、上游原生支持的线路格式（可多选，New API 这类网关三种都勾）、模型列表或「接受任意模型」。

选分组时先按 model 过滤，再要求分组支持这个请求的线路格式。都不支持时，只有在分组允许转换的情况下才走转换兜底。没有 model 的请求（例如列音色）走访问密钥绑定的分组。

### 3. 按调度策略选 key

每个分组可以选轮询、加权随机或按会话粘性。冷却、失败换 key 和 429 退避沿用现有实现。

另外新增「资源粘性」。上游返回带 `id` 的资源（文件、批任务、视频任务、存储的 Response）时，记下 `id → 分组 + key`，之后带这个 id 的请求必须回到同一把 key。视频生成这类异步接口依赖这一点，否则查询进度会随机落到别的 key 上找不到任务。

### 4. 原样转发

- 上游 URL 等于分组地址加下游路径，版本段按已经实现的规则规整。
- 鉴权头按线路格式改写，OpenAI 用 `Authorization`，Anthropic 用 `x-api-key`，Gemini 用 `x-goog-api-key`。下游带来的鉴权头全部去掉。
- 请求体默认一个字节不改。分组开了模型映射才改 model 字段。
- 响应按字节流回，SSE、音频、图片二进制都一样。
- 计费从响应里旁路读取用量（OpenAI `usage`、Anthropic `usage`、Gemini `usageMetadata`），读不到就只按次记录。

## 需要你决定的事

### A. 数据面怎么落地

| 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| A1 增量（推荐） | 保留现有强类型路由处理聊天四种格式，新增通用透传通道接住其余所有路径；补上 OpenAI 兼容渠道的原生 Responses | 改动集中在新增文件，还能继续合并上游 GPT-Load | 两套路径并存，概念多一层 |
| A2 重写 | 数据面整体换成上面四层，强类型路由只留给转换兜底 | 结构最干净，和定位完全一致 | 上游的数据面改动基本无法再合并，只能挑着搬；工作量大，回归风险高 |

我建议先做 A1。聊天四种格式在格式一致时已经是透传，真正的缺口在其余接口和 Responses。A1 补上之后再看要不要走到 A2。

### B. 渠道类型怎么处理

现在有 37 个渠道预设。按新结构，大部分 API key 类渠道可以收成一个「通用上游」，预设只负责填默认地址、线路格式和鉴权方式。

难点在特殊鉴权渠道，包括 Codex、Claude、Gemini 订阅的 OAuth 登录，Antigravity，Grok，AWS Bedrock 的签名，Vertex 的服务账号，Azure 的部署路径。这些需要单独的鉴权适配器，没法简化掉。

需要你告诉我实际在用哪些。不用的可以先在界面里隐藏，减少配置时的干扰。

### C. 未知路径放不放行

| 选项 | 说明 |
|---|---|
| C1 全放行（推荐） | 表里没有的 `/v1/**` 都按 OpenAI 格式转发，后台列出最近出现的未知路径，方便补表 |
| C2 仅放行登记过的 | 更安全，新接口要先在后台加一行 |

两种都会默认拦下组织管理类路径（`/v1/organization/**`、`/v1/admin/**`）。

### D. 有状态接口

| 选项 | 说明 |
|---|---|
| D1 资源粘性（推荐） | 按上面「资源粘性」记录 id 和 key 的对应关系，文件、批任务、视频都能正常用 |
| D2 不支持 | 这些路径直接拒绝，实现最简单 |

### E. 重试边界

上游还没返回任何字节时可以换 key 重试，流开始后不再重试，这一点没有争议。待定的是未知路径遇到 5xx 要不要重试，因为未知接口可能不是幂等的。我建议只对连接失败和 429 重试，5xx 直接返回。

## 分阶段

1. 整理主分支（进行中），把 v2 切为 main，跑通 CI，统一 base_url 版本段。
2. 合并上游 GPT-Load 10-06 之后的 40 个提交。
3. 通用透传通道，包括接口表、按 model 选分组、鉴权改写、字节流转发和旁路用量。
4. 资源粘性，接上视频、文件、批任务。
5. OpenAI 兼容渠道的原生 Responses，以及日志里的透传和转换标记。
6. 渠道配置收敛，按 B 的决定处理。
