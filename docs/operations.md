# 发布、升级与恢复

本指南描述 API-Load 的通用操作流程，不表示某个实例已经完成部署。当前源码准备 2.1.2 候选版本，公开版本和镜像以仓库 Release、容器注册表及所选镜像的 revision 为准。环境地址、账号盘点、凭据、数据库导出和详细操作报告由部署者在仓库之外保存。

## 选择版本

正式版本使用 `vX.Y.Z` 标签。`ghcr.io/thewisewolfholo/api-load:2` 跟随 2.x 正式版，`edge` 跟随 main。需要可恢复的部署时，应固定正式版本或 image digest，并记录当前运行 revision；源码版本号本身不能证明公共镜像已经发布。

升级沿用现有 Go 程序、数据库和加密材料。保留 API-Load 品牌、图标及上游版权声明，不需要为了新增原生接口或透明转发更换框架。

## 升级前检查

1. 记录当前程序版本、镜像摘要、数据库类型和迁移版本，保存部署配置及挂载关系。
2. 备份数据库、`DATA_DIR` 和恢复所需加密材料。备份放在受保护的私有目录，不提交到 Git，也不写入公开报告。
3. 在隔离网络恢复数据库副本，用相同加密材料确认旧凭据可读，并检查现有分组、模型映射、访问令牌和价格配置。
4. 对副本运行候选程序，核对迁移结果及配置差异。SQLite、MySQL 和 PostgreSQL 应按实际使用的数据库分别验证，不能用一种数据库的结果代替另一种。
5. 检查请求格式、授权、目录同步和代表性响应。模型目录成功、HTTP 成功、结果完整与质量通过应分别记录。

仓库的 `scripts/verify-native-container.py` 可对已有本地镜像执行 Linux 与 PostgreSQL 合成数据升级检查。它使用隔离网络和临时数据，不自动拉取镜像。这个结果不替代生产数据副本检查。

## 切换与验证

在约定的维护窗口切换程序或镜像，保留当前数据库及卷。不要用空库替换已有数据，也不要通过自动扩大旧令牌权限来启用新接口。

切换后核对健康接口、管理鉴权和运行 revision，再检查旧配置与代表性请求。使用合成文字、图片或文件，限定供应商、型号、次数和成本。HTTP 429 表示请求受限，应记录失败并停止未获授权的重试；它不能算作结果或质量验证成功。

优先让下游使用自己支持的原生或兼容接口。透明 HTTP 需要单独授权，适用范围见[透明转发说明](transparent-forwarding-proposal.md)。不要为了改用透明入口而放弃已有模型授权、结构校验或用量解析。

临时验证令牌应设置最小分组、协议及路径范围，验证后删除并确认结果。删除失败时保留非敏感令牌编号和失败状态供管理员处理，不能报告已清理。

## 恢复

恢复前停止写入，并保留当前状态供审查。先确认旧程序是否兼容新迁移；兼容时可以恢复旧镜像而保留当前数据库。不兼容时，在隔离环境验证数据库备份和原加密材料后，再按维护计划恢复。

需要恢复客户端连接时，只还原本次改动的地址与访问令牌。先检查当前配置是否仍属于这次操作，避免用整库旧快照覆盖后来产生的模型选择、索引或其他设置。

恢复完成后重新检查运行 revision、凭据解密、旧访问令牌及代表性请求。保留必要恢复材料到回退窗口结束，清理时只处理此次创建且已确认不再使用的资源。

## 可公开的维护资料

公开文档可以保留协议契约、官方来源、合成测试方法、软件限制和版本兼容说明。真实域名、机器用户名、主机和数据库名称、账号组合、凭据数量、访问令牌编号与私有备份位置应放入部署者自己的运维资料。
